# Parousia Architecture

This document describes how Parousia's pieces fit together. See `project/vision.md` for why they exist and `project/roadmap.md` for when each part gets built.

## Overview

Parousia is four cooperating pieces: the browser extension, Parousia Desktop, platform adapters, and Activities.

The browser extension watches tabs and detects activity on supported sites, producing generic `Activity`/`Presence` values (see `browser/src/core/`). It doesn't know or care which platform will eventually display that presence.

That `Presence` travels across a transport (see Communication Protocol) to whatever owns publishing to real platforms. Normally that's Parousia Desktop, a native Rust application, but the extension is also meant to work with compatible third-party backends (see Compatibility Layer) so people aren't forced to run Parousia Desktop.

Parousia Desktop hosts platform adapters (see Platform Adapter Architecture). Each adapter translates a generic `Presence` into whatever a specific platform's Rich Presence integration expects. Discord is the first one.

Activities are the detection layer: a matcher (usually a URL pattern) plus logic that turns a page into an `Activity`. Parousia Activities sit alongside compatibility support for the existing PreMiD Activities ecosystem, so the project isn't stuck reimplementing site support that already exists elsewhere (see Compatibility Layer).

This split keeps every piece replaceable on its own: a new platform is a new adapter, a new site is a new Activity (native or via PreMiD), a new browser is a new target under `browser/src/platforms/`. None of them need to touch the others.

## Security Model

Every boundary between components is untrusted until proven otherwise:

- **Browser extension.** Content scripts, and anything that touches page content, are the least trusted part of the system. Native Activities read only the URL and title, and page data from Parousia's own collector where the user granted the site. PreMiD Activities run third-party code as content scripts, only on sites the user granted; the background treats everything they send as untrusted, and neither the UI port nor storage is theirs to use (the UI port checks the sender is an extension page; storage is limited to extension pages where the browser allows it, and PreMiD's runtime takes the storage API out of the world their code runs in everywhere else). Their code comes from the source repository's `main` at build time, compiled unchanged, with the revision recorded.
- **Browser ↔ Desktop channel.** Desktop only talks to recognized Parousia builds, identified by what the browser itself vouches for: the WebSocket `Origin` header, which pages and other extensions can't forge. There are no pairing codes or shared secrets. The WebSocket listens on `127.0.0.1` only, and on Linux Desktop refuses connections from other OS users. A process running as the same user can claim any identity; that's out of scope for this channel, as for any local app. `project/threat-model.md` has the full threat model.
- **Parousia Desktop.** The trusted core. It validates and bounds anything coming from the browser (size limits, expected shape) before handing it to an adapter, and doesn't assume an adapter's output is safe to log or display without care.
- **Platform adapters.** Talk to a specific platform's local integration (Discord's local RPC socket, for example). They receive only the generic `Presence` the runtime built, never raw page content. Discord's socket is used only when this OS user owns it, and what Discord sends back is bounded and read into a few known fields.
- **Dependencies.** Kept minimal by policy. CI runs CodeQL, Dependabot, `bun audit`/`cargo audit`, and PR-time dependency review so a known-vulnerable dependency doesn't quietly creep in (see `.github/workflows/`).
- **Secrets.** Never committed. There currently aren't any: Discord's local RPC is keyed by a public application ID, not a secret.

This is a model, not a guarantee. It should be revisited whenever a new component or transport is added, and it gets a dedicated pass during release hardening (see `project/roadmap.md`).

## Activity System Architecture

An **Activity** describes one thing a user might be doing on a specific site: an id, a display name, optional details/state text, the URL it was detected on, optional assets/timestamps, up to two buttons, and links for its details and state lines (`browser/src/core/activity.ts`).

### Where Activities Come From

The main repository has no Activities of its own; it has the API they're written against and the runtime that runs them. Activities come from two repositories, each followed at its `main` branch (`browser/activity-sources.json` names the repository and branch) and checked out by `bun run activities:fetch`:

- **Native Activities**, [parousia-project/activities](https://github.com/parousia-project/activities). Jena Hub (`websites/J/Jena/`) is the first.
- **PreMiD's Activities**, [PreMiD/Activities](https://github.com/PreMiD/Activities).

Everything is included when the extension is built (`browser/scripts/activities/`). Nothing is downloaded at runtime: MV3 doesn't allow extension pages to run remote code, store policies forbid it, and what's included is what each repository's `main` holds when the build runs. Every build (and `bun run activities:fetch`, and `activities:check`) moves each checkout there first, so a build never uses an older copy than the network has; it retries, and a fetch that fails (or brings a commit with no `websites/` folder) leaves the last working checkout untouched, so only a machine that never fetched has nothing to build from. The revision each source was at goes into the build (the catalog's `sources`, PreMiD's `SOURCE.txt`, and a release's notes) so a bug can be traced to a commit; it is a record, not a pin.

`bun run activities:check` runs the whole pipeline, lists every PreMiD Activity left out and why, and type-checks native Activities against the API.

### One Pipeline

Both sources go through the same steps, and they're told apart only where PreMiD's API genuinely differs:

1. **Discovery.** Both repositories file one folder per website, `websites/<letter>/<Name>/` (PreMiD's layout, which the native repository follows too), so one walk finds both (`discover.ts`, `pipeline.ts`). The folder's name, as an id (`YouTube Music` is `youtube-music`), is the website's identity in either source.
2. **Metadata.** Each folder is read by its source's adapter (`native.ts`: `metadata.json` plus `activity.ts`; `premid.ts`: PreMiD's `metadata.json`, `presence.ts`, optionally `iframe.ts`, or a `v1/` folder of those). An adapter only maps its source's own names (PreMiD's `service`, `url`, `logo`, `altnames`, `tags`; a native Activity's `name`, `matches`, `icon`) onto one draft; `metadata.ts` turns the draft into the same **manifest** (`browser/src/activities/manifest.ts`) for both, with one set of limits, settings rules, sites to ask for, and search words: the catalog entry (`ActivityInfo`), a matcher, and for PreMiD's, its script. A native problem stops the build; a PreMiD Activity that doesn't fit is left out and listed.
3. **Websites in both sources.** When a native Activity and a PreMiD one share a folder name, each gets the list of both (`ActivityInfo.variants`, native first; `linkVariants`). The identity is the folder name as an id with punctuation and spacing left out (`websiteKey`: `Discord.js`, `DiscordJS`, and `Discord JS` are one website), never an Activity's display name, and never the sites it covers. A name with no letters or digits identifies nothing, and two native Activities whose names differ only in punctuation stop the build. Only the one chosen runs (the native one until someone picks PreMiD's, from the Activity's page), and the dashboard lists the website once. A site two differently named Activities happen to cover isn't a pair: the first registered runs there, as before.
4. **Packaged files.** One catalog for the dashboard's list (`activities/catalog.json`: what a card shows, searches, and needs to turn an Activity on, without settings, page data, or Discord Applications), one manifest per Activity (`activities/native/<id>.json`, `activities/premid/<name>.json`), an index of them by id (`activities/index.json`), and an index by host name (`activities/hosts.json`) for the popup to find the Activity for a tab.
5. **Matching.** Match patterns (native `matches`) and PreMiD's `regExp` compile through one function, and every Activity is registered the same way (`registered()`); native Activities come first.
6. **Settings.** One model (`boolean`, `choice`, `text`, `number`, with `when` conditions), checked by one set of rules (`checkSetting`); PreMiD's settings are mapped into it (`values` become a choice kept as its index, `if` becomes `when`, and its language picker is fixed to English, since PreMiD's translations live on its servers). The dashboard's Activity page and the popup render them with the same code (`browser/src/shared/activity-settings.ts`).
7. **Permissions.** One model for both: the sites an Activity reads pages on, asked for when it's turned on (below).
8. **Running.** One host (`browser/src/activities/host.ts`) runs whatever an Activity needs in the active tab's page: Parousia's collector for a native Activity that takes page data, or a PreMiD Activity's own script. Both go through the same checks, injection, message parsing, and site access, and what comes back becomes the page the runtime hands the Activity.

### Registry and Runtime

A **PresenceRuntime** resolves the registry against the current tab, skipping Activities that can't run there (off, not the chosen implementation of their website, or reading pages on a site that isn't granted), hands `detect` the Activity's settings, and wraps the result (or nothing) into a **Presence** with a timestamp (`browser/src/core/runtime.ts`, `presence.ts`). Where no Activity has anything to share, it shares the Default Activity instead, if one is set up (below). It stamps the catalog's `discordClientId` on the Activity; only a PreMiD Activity's own script may pick another, and only among the Applications its source names. Without one, Parousia's own Application is used. A `detect` that throws shows nothing rather than stopping detection. `Presence` is the unit that leaves the browser, and it's platform-agnostic; the page an Activity is about (`Activity.url`) stays in the browser.

Which Activities are on, their settings, and which implementation of a website was chosen are kept in `chrome.storage.local` under `activities` (`browser/src/core/activity-state.ts`). An Activity that reads only URLs and titles is on until turned off; one that reads pages (every PreMiD Activity, and native ones that declare page data) is off until turned on, since turning it on asks for its sites. The dashboard lists every website once, with a switch on each card, and each Activity has its own page: whether it's on, where it stands with site access, which implementation runs when both sources have the website, and its settings (`browser/src/fullscreen/`).

The Activities page (`browser/src/fullscreen/activities.ts`, with the pure logic in `browser/src/shared/activity-list.ts`) lists enabled Activities first and disabled ones after, each by name (numbers in order) and then by id, so the order never depends on how the catalog was built. A Filter button beside the search bar offers Enabled, Disabled, Parousia Activities, and PreMiD Activities; choices in one group add up and the two groups narrow each other, and a website in both sources is filtered as the implementation its card shows. The query, filters, and page live in the address. The order is worked out when the page loads and when you search or filter, not when you switch a card, so a card doesn't leave your cursor the moment you turn it on. "Enable or disable all" is a quiet link under the search that opens a panel; it applies to everything matching the search and filters, on every page, and each action asks once more, with the count and, for enabling, a warning that the browser will ask for access to that many sites in one prompt. That prompt is a single request (`permissions.request` takes all or nothing), made from the confirming click. Activities that need no new site are turned on either way, ones whose sites were declined stay off and say so, and the grants are read back after an answer rather than trusted, so nothing is marked on for a site the browser didn't grant. Disabling gives back the sites only the disabled Activities used, and every change is one storage write.

The popup and dashboard show what the background is sharing, pushed over their port with every change, along with whether the Activity has settings of its own. The popup shows "Current activity" only while something is shared, with "Configure activity" for an Activity with settings. When nothing is, it looks up the tab's site in the host index and, if an Activity covers it but isn't running (turned off, or on without its site), shows that Activity and one button to fix it ("Turn on" or "Allow access"); otherwise one line says there's nothing to share. The popup follows the last focused browser window, and so does the background: what's shared is the active tab of the focused window, never a tab switched to in another one.

Lifecycle: a tab's `Presence` updates on navigation, on a title change when the page is one an Activity looks at (single-page sites often set the title a moment after the URL), and when something the host runs in the page reports a change. It clears (a `Presence` with no activity) when the tab closes, hides, or navigates somewhere unmatched. The runtime always sends an explicit "nothing" rather than going quiet, so a stale presence doesn't linger on a platform after someone's moved on. Privacy settings (`browser/src/core/preferences.ts`, set from the extension's Settings) shape what's published: with Share Media Details off, only the Activity's name, link, and images leave the browser (no details, state, image captions, detail or state links, or buttons); private windows share nothing unless Incognito Behaviour is set to share; and Idle Timeout keeps presence for up to that many minutes after the browser loses focus instead of clearing it at once. Away from the browser, what's shared keeps following the active tab, and sound playing in that tab keeps it shared without a time limit: music doesn't stop because someone opened Discord or the popup. Once the timeout runs out, nothing is shared again until the browser has focus or sound plays.

### Page Data and Site Access

By default an Activity reads the page's URL and title, which the `tabs` permission already exposes. Reading the page itself takes two things, both explicit:

- **Site access**, asked for when an Activity is turned on: turning on an Activity that reads pages asks the browser for its sites (its `origins`), in the same click, through the browser's own prompt. Declined, it stays off, and its card, page, and the popup say why. Taken back later (from the browser's own settings for the extension), it stays on but is unavailable where it lost access: nothing runs there, it shows as needing access, and "Allow access" asks again. Activity pages have no site switches of their own. Settings > Site access has "Access your data for all websites", which covers every site at once; it's off by default, and only ever asked for by its own switch. It doesn't list or revoke individual sites: those grants belong to the browser, which doesn't let an extension take back every kind of grant (a site inside a broader grant, or one the user limited in the browser's own site-access setting, can't be carved out or reliably read back), so a list here could say something the browser doesn't. Both are optional permissions (`optional_host_permissions: ["*://*/*"]`, `optional_permissions: ["scripting"]`), so nothing is granted at install. Turning an Activity off, or choosing the other implementation of its website, gives back the sites no other Activity that's on needs, and `scripting` once nothing does.
- **What Activities may read**, one choice for all of them in Settings > Privacy: `media` (what's playing), `thumbnails` (images of it), `creatorIcons` (pictures of a channel or creator). Each Activity declares the kinds it takes; a kind switched off is never read by Parousia's collector and never shown from a PreMiD Activity's own reading.

The host reads which sites are granted from the browser (`permissions.getAll()`, `browser/src/core/site-access.ts`), and follows every change: taking a site back stops whatever runs there at once. An Activity that reads pages is found only on pages whose site is granted (`canRun`); on those, the runtime hands it `granted`, the kinds it has there:

- A **native** Activity gets exactly its granted kinds from Parousia's collector (`browser/src/activities/collector.ts`): for `media`, the page's Media Session (title, artist, album, and its own word on whether it's playing) and its `<video>`/`<audio>` (duration, and the clock); for `thumbnails`, the largest `https` artwork or `og:image`. No Activity code runs in the page, and nothing it didn't declare, or that's switched off, is read.

  The collector is the one Media Session reader, shared by every native Activity that declares `media`, and it runs only in a tab where one does (injected on demand, never at install). It reads once a second while the page is visible and sends only changes. The clock goes out as ready-made `start` and `end` timestamps (Unix milliseconds, rounded to the second) that change only when playback is paused, seeked, or restarted, so a song playing through sends nothing and an Activity keeps no clock of its own. A page that sets no session gives no title, and the Activity falls back to the URL and the tab's title (YouTube Music's does). An Activity for a site whose markup is unstable should prefer this over reading the page itself, which is what a PreMiD Activity does.
- A **PreMiD** Activity's own code reads the page directly, so kinds switched off are held back on the way out (`limitPageData`: `media` removes details, state, their links, buttons, times, captions, and a name it set from the page; `thumbnails` a large image from the page; `creatorIcons` a small one), while its own images (Discord asset keys, PreMiD's asset host) stay.

Browsers differ here: Chromium and Firefox both grant optional host access at runtime through `permissions.request` from a click. Firefox closes its popup when the prompt opens, so the popup saves the Activity as on before asking: if the prompt is declined, the Activity shows as needing access rather than silently staying off. Content scripts get no access to the extension's storage where the browser can restrict it (`storage.local.setAccessLevel`, Chromium); in every browser, PreMiD's runtime removes the storage API from the world PreMiD code runs in before any of it runs (`withholdStorage`, checked in Firefox by `activities:firefox`). The UI port only answers extension pages.

### Default Activity

A presence written by hand in the dashboard's Default Activity tab (`#default`, between Activities and Settings; `browser/src/core/default-activity.ts`, `browser/src/fullscreen/default.ts`), shared whenever the tab in front has no Activity: a site none covers, a browser page, a new tab. It's the runtime's fallback, so it goes through the same pipeline as a detected Activity: Privacy settings, private windows, the idle timeout, Settings > Platforms, and both ways to Discord. It has a name (required), details, state, images (an `https` link, or an asset of the person's own Discord Application), up to two buttons (`http(s)` links), elapsed time (counted from when it started showing, kept across tab changes), and optionally its own Discord Application. The form saves only what can be shown, and Desktop checks it again like any Presence. It's kept in `chrome.storage.local` under `defaultActivity` and has an id no Activity can have (`parousia:default`).

### Native Activities

`metadata.json` names the Activity (its `id` is the folder's name in lowercase words joined by `-`), lists its pages as WebExtension match patterns (`https://jena.systems/*`; never every site), and may declare an `icon`, `data` (`media`, `thumbnails`), settings, and a Discord Application. One that declares `data` reads pages, so it's off until turned on, which asks for the sites its patterns name. `activity.ts` exports `detect(page, settings)`, where `page` is the URL, the title, `granted`, and the page data it has. That's Activity API version 1 (`browser/src/core/api.ts`, `import type … from "parousia"`); the activities repository keeps its own copy (`types/parousia.d.ts`), and `activities:check` type-checks every Activity against this one so the two can't drift apart. The modules are bundled through a generated module, `parousia:activities`, into the background script and the userscript (which uses URLs and titles only). The format, rules, and testing helpers for writing one are in that repository's `.github/CONTRIBUTING.md`.

### PreMiD Activities

A PreMiD Activity is a script written against PreMiD's `Presence` class: it builds `PresenceData` on every `UpdateData` tick from the page's DOM and calls `setActivity`. Parousia runs these unchanged:

- **At build time** (`browser/scripts/activities/premid.ts`), every `clientId` in its source is kept (literal ids and enum members, as PreMiD's own check finds them; the first is the default), its logo becomes its icon, and it declares all three page data kinds, since its code can read any of them. `presence.ts` and `iframe.ts` are compiled with Bun's bundler (the `premid` helper import resolves to PreMiD's own package in the same checkout) and wrapped so the names `Presence` and `iFrame` are Parousia's, bound to that Activity. The build packages each script, its manifest, an index so the background reads only the ones that are on, `activities/premid/runtime.js`, and PreMiD's license with the source commit. Activities that need their own npm packages, name no client id, target API version 2, or are on PreMiD's DMCA list are left out and listed.
- **In the page** (`browser/src/premid/page.ts`, injected before the Activity's script, in the content-script world): `Presence`, `iFrame`, `Slideshow`, and PreMiD's deprecated helpers. It first takes the storage API out of that world (`withholdStorage`). It ticks once right away and then once a second while the page is visible, runs the Activity's `UpdateData` listeners without overlapping, and sends `PresenceData` (text read out of nodes, image and link elements as URLs, dates as numbers) only when it changed. An Activity that stops updating while its page is shown has its last report dropped (after 30 seconds, or 6 after the page's address changes), since an Activity that no longer understands its page, after a site changes its markup, would otherwise leave "Browsing home" under a song that's playing. The background closes a script's channel when its Activity is turned off or its site taken back; injected again, the script runs anew instead of staying dead until a reload. `getSetting` answers from what the background sends (and updates live), `getStrings` from PreMiD's English strings, and `getPageVariable` and `execInPage`'s declarative form (`{ get }`, `{ call }`) from the page's own world, where the background runs a fixed function (`browser/src/activities/page-world.ts`) that never follows a path through `__proto__`, `constructor`, or `prototype` and never calls a function that runs text as code (`eval`, `Function`, `setTimeout`, and the like). `execInPage` with a function (which would need the page to evaluate code), `onRequest`, and log reading aren't provided, so an Activity's `supports()` check sees them missing. Blob images need an image host (PreMiD uploads them to its own), so its icon shows instead.
- **In the background**, the host serves its ports only from this extension's content scripts in a tab, for an Activity that's on (and the chosen implementation of its website), whose site is granted, and that matches the page the port came from (iframe ports: an Activity with an iframe script, in a frame its `iFrameRegExp` matches). Every message is parsed and bounded (`browser/src/activities/messages.ts`, `browser/src/premid/presence-data.ts`), and an iframe's data goes only to the same Activity's page script in the same tab.

What PreMiD's `PresenceData` carries that Parousia's `Activity` doesn't yet is left out: the activity type (Listening, Watching), `statusDisplayType`, party size, and links on the images. Carrying them means a protocol change to Desktop.

## Platform Adapter Architecture

An adapter is anything that can take an Activity and make some platform show it. On the desktop side, that's a small Rust trait (`desktop/src/platform.rs`):

```rust
pub trait PlatformAdapter: Send + Sync {
    fn platform(&self) -> Platform;
    /// What to show now, or nothing. Returns at once.
    fn show(&self, activity: Option<Activity>);
    fn status(&self) -> AdapterStatus;
}
```

Desktop's Hub decides what each platform shows, so an adapter only ever deals with one Activity. Of the connections whose Presence may go to that platform, the one whose Activity changed most recently wins; when it clears or disconnects, the next most recent still-current Activity takes over. Each browser says which platforms its Presence may go to (Settings > Platforms, sent with every Presence); the userscript doesn't choose, so its Presence may go everywhere. An adapter is only told about actual changes, and `show` must return at once: it's called with the Hub's lock held, so updates reach it in order, and all waiting (connecting, retrying, pacing) happens on the adapter's own thread. `status` reports idle, connecting, connected, showing (with the Activity's name), not running, or refused (with the platform's reason), which the CLI, the tray, and the extension's Settings > Platforms show.

**Discord** (`desktop/src/discord/`) talks to the Discord app's local RPC: a Unix socket (`discord-ipc-0` to `9`) on Linux and macOS, a named pipe on Windows. The format is an 8-byte header (opcode and length) and JSON, so it needs no crate. Desktop looks in `$XDG_RUNTIME_DIR`, `$TMPDIR`, `$TMP`, `$TEMP`, and `/tmp`, each with Discord's Flatpak (`app/com.discordapp.Discord`, Canary) and Snap (`snap.discord`, Canary) directories, and uses a socket only if this OS user owns it. `PAROUSIA_DISCORD_IPC_DIR` replaces the search with one directory; the end-to-end checks use it to point Desktop at a fake Discord.

- A worker thread owns the connection. It starts when there's something to show and ends once there's nothing to show and no connection, so an idle Desktop has no thread for Discord. It connects only when there's something to show, and lets go 30 seconds after clearing, so switching tabs doesn't reconnect.
- Discord not running: it tries again after 1 second, doubling to 30, and right away whenever the Activity changes. A restart closes the socket, which a reader thread notices at once on Linux and macOS; the current Activity is shown again once Discord is back. A synchronous Windows pipe can't be read on one thread while another writes, so there replies are read right after each request and a restart is noticed at the next update.
- Discord accepts 5 activity updates per 20 seconds. Faster changes are coalesced: only the latest is sent once the window allows.
- Discord binds a connection to one Application, so an Activity with its own `discordClientId` reconnects as that Application. Without one, Desktop uses `discordClientId` from `config.json`, or Parousia's own Application.
- A handshake Discord refuses (an unknown Application, say) is reported and tried again later; an activity it refuses is reported and not resent, since the same one would be refused again. Discord's `READY` carries the signed-in user; Desktop doesn't keep it.

Discord refuses a whole activity over one bad field, so the mapping leaves out what it can't take: text under 2 or over 128 characters (cut to 127 and "…"), images over 256, links that aren't `http(s)` or are over 256, more than two buttons. The rules are in `desktop/src/discord/activity.rs` and in the extension's `toDiscordPresence` (for Discord-RPC-Extension's app), and both are tested against the same cases, `adapters/discord/activity-mapping.json`. The limits were checked against a real Discord, which also accepts `name`, links on the details and state lines, and image URLs (it proxies them).

Fluxer and Stoat are planned but intentionally not started yet. Because every adapter takes the same `Activity`, adding one later means writing a new adapter, not touching the runtime, the registry, or any existing adapter.

Concrete platform adapters are Desktop code and live under `desktop/`. The top-level `adapters/` directory holds only shared, platform-level definitions: `adapters/discord/activity-mapping.json` so far. The browser and Desktop each keep their own `Presence` types with the wire format as the shared contract (see Communication Protocol), so the top-level `core/` placeholder has no role.

## Communication Protocol

The browser and Desktop speak one small protocol over one channel: a WebSocket on the loopback interface.

### Channel

`ws://127.0.0.1:57179/ws`, a fixed port in the IANA dynamic range, away from common development ports and Discord's own `6463-6472`, bound to `127.0.0.1` only. Every client uses it: Chromium, Edge, and Firefox extensions (sandboxed Flatpak and Snap builds included), the userscript, and on every OS. No extension permission is needed for it (the extension's CSP `connect-src` names it), so the extension asks for nothing beyond `tabs` and `storage`.

Desktop also has a user-private IPC socket (`$XDG_RUNTIME_DIR/parousia/desktop.sock`, 0600 in a 0700 directory; the data directory where there's no runtime directory). Browsers never use it: it carries the CLI's control requests and is the single-instance check.

**Why only a WebSocket.** The userscript and sandboxed Flatpak and Snap browsers can only reach Desktop over the network, so a loopback listener has to exist regardless. A Native Messaging channel was built next to it during Phase 3 and dropped before release, because a second channel didn't earn its cost:

- It needs the `nativeMessaging` permission, which browsers show as a separate install warning ("Exchange messages with programs other than Firefox").
- It needs a host manifest per browser and per OS (a directory per Chromium fork on Linux and macOS, the registry on Windows), a relay process per connection, and a second connection path in the extension that doubles the test matrix.
- It doesn't reach the clients that most need an alternative: Flatpak and Snap browsers and the userscript.
- Its one technical advantage, keeping Firefox's MV3 event page alive, has a simpler answer. Measured with Firefox 150 (idle timeout shortened to 6 s): an open WebSocket with messages every 4 s doesn't keep an event page alive and an open Native Messaging port does, but so does calling `runtime.getPlatformInfo()`. On Chromium 152 (default 30 s timeout, no DevTools attached) that call alone kept a service worker alive for 95 s. One background keepalive covers both engines (see Connection Lifetime).
- Identity is the remaining difference: Native Messaging names a Firefox caller by its stable add-on id, while its WebSocket `Origin` is random per install, so each Firefox install is allowed once (see below), the same one-time step registering a host would be.

### Recognized Builds

Desktop accepts a connection only from an identity it recognizes:

| Client             | Identity (the WebSocket `Origin`)                                                 | Recognized when                                                                                   |
| ------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Chromium extension | `chrome-extension://<id>`                                                         | It is the Chrome Web Store build (its id is built in), or listed in `allowedOrigins`              |
| Firefox extension  | `moz-extension://<uuid>`, random per install                                      | It's listed in `allowedOrigins`: allowed once per install, from the tray, the CLI, or the console |
| Userscript         | The page's origin; Firefox reports a content script's WebSocket as `Origin: null` | Only while "Allow userscripts" is on (off by default)                                             |

`allowedOrigins` holds exact `chrome-extension://<32-letter id>` and `moz-extension://<uuid>` origins, nothing broader. A malformed entry stops Desktop at startup rather than being skipped.

There is no Safari build. Its extension origin changes every launch, so Desktop couldn't recognize it, and shipping one means Apple's developer program and an Xcode wrapper that relays through the containing app. The extension sticks to standard WebExtension APIs (`chrome.*`), so a Safari target stays possible later, but nothing builds, tests, or releases one.

The WebSocket upgrade is decided before it completes. A recognized extension origin, or a web origin while userscripts are allowed, gets through. An extension origin Desktop doesn't recognize gets exactly one `reject {reason: "origin_not_allowed"}` and a close: a browser can't tell a refused upgrade from nothing listening, and "allow this build" has to be something its popup can say. Nothing it sends is read, and Desktop lists it (with a notification) so the person can allow it in one step. Web origins while userscripts are off, a `null` or missing origin, and anything malformed get a bare `403` with no body, so a page learns nothing beyond the refusal.

### Messages

Every message is a small JSON object parsed into strict types (unknown fields are an error); every frame, in both directions, is capped at 16 KiB.

1. The client sends `hello {protocolVersion: 6, name}` within 5 seconds. `name` ("Firefox on Linux") is display-only and untrusted.
2. Desktop answers `welcome {protocolVersion}`, or `reject {reason}` and closes.
3. Then `presence {presence, platforms?}`, `ping {}` (answered with `pong`), `status {}` (answered with `status {status}`, Desktop's report), and `set {setting, value}` (answered with the new report), until either side closes. `platforms` lists where the Presence may be shown (`discord`, `fluxer`, `stoat`); without it, everywhere. A malformed frame gets a non-fatal `reject`; more than a burst of 20 messages, refilling at 5 per second, gets `rate_limited` and a close.

`status` and `set` are for extensions only: a userscript is any web page, so it can publish Presence and nothing else. `set` also needs a connection Desktop knows comes from this OS user (on Linux, where the loopback peer's owner can be looked up; elsewhere, settings change from the tray, CLI, or console). The only setting is `allowUserscripts`. The extension doesn't send `ping`; it's there for liveness checks and tests. Reject reasons: `unsupported_version`, `malformed`, `timeout`, `origin_not_allowed`, `rate_limited`, `not_permitted`.

When Desktop gives up on a connection it stops sending, then reads and discards what the client still sends for up to a second before closing. Closing a socket with unread input makes the kernel reset the connection, and a reset can destroy the `reject` just sent before the client reads it.

### Presence

Desktop keeps the latest Presence per connection and drops it when that connection closes, so a browser that goes away stops showing as doing something. A Presence carries only what a platform shows: since protocol 6 the page an Activity is about stays in the browser (nothing on Desktop's side used it), and the extension builds each Presence it sends field by field (`presenceWire`), so nothing it keeps for itself leaves by accident. Presence fields are length-limited, links (the details and state lines, buttons) must be `http(s)`, times must be non-negative, a `discordClientId` must be a Discord id, and there are at most two buttons, before anything else sees them. Disallowing an origin, or turning userscripts off, closes the connections that relied on it immediately.

### Connection Lifetime

The browser connects only while something needs Desktop: an Activity is being reported, or a popup or dashboard is open (their port to the background script). Otherwise it lets go 30 seconds after the last need, so an idle browser holds no socket, sends no traffic, and lets its MV3 background be suspended. While an Activity is being shared, the background script calls `runtime.getPlatformInfo()` every 20 seconds (`backgroundKeepalive` in `browser/src/platforms/background.ts`), which resets both Chromium's and Firefox's idle timer; nothing goes over the socket for it. Without it, Firefox stops the event page about 30 seconds after the last tab event, which closes the WebSocket and makes Desktop (and Discord-RPC-Extension's app) drop the presence while someone is still on the page. When Desktop is unreachable while needed, retries come every 10 seconds on in-memory timers. When nothing needs Desktop, nothing retries, and a suspended background simply starts over the next time it's needed, so there's no persisted schedule and no `chrome.alarms`. After `origin_not_allowed` or `unsupported_version` the extension stops retrying until a popup or dashboard opens, since retrying can't change the answer. The userscript lets go immediately when its page is left (`pagehide`), since a page in the back/forward cache has its timers frozen.

Extension pages carry an explicit Content Security Policy: `script-src 'self'; object-src 'self'; connect-src 'self' ws://127.0.0.1:57179 ws://127.0.0.1:6969`. Firefox's default MV3 policy includes `upgrade-insecure-requests`, which silently turns `ws://127.0.0.1` into `wss://` (a TLS handshake neither server can answer). The `connect-src` also limits extension pages to exactly two endpoints: Desktop, and Discord-RPC-Extension's app (see Compatibility Layer).

### Desktop Internals

No async runtime: the workload is a handful of long-lived, mostly idle connections. One thread accepts TCP connections, one accepts CLI connections on the IPC socket, each connection runs its own blocking thread, the Discord adapter runs one only while it has something to show or is still connected (plus a reader while connected, on Linux and macOS), and the tray (Linux, Windows) owns the main thread. Idle, nothing wakes up: no timers, no polling. Accepting is rate limited (a burst of 32, refilling at 16 per second, checked when a connection arrives), at most 64 connections are open at once, and request heads time out after 5 seconds. On Linux, each TCP connection's owner is looked up in `/proc/net/tcp` before anything is parsed: another user's connection is dropped, and one that can't be found is treated as another user's. The WebSocket side is `tungstenite` plus `httparse` over plain `std::net`; `GET /health` is the one plain-HTTP route.

Settings live in `config.json` in the data directory (`allowedOrigins`, `allowUserscripts`, and optionally `discordClientId`; 0600, written through a temp file, fsync, and rename). An unknown key, a malformed origin, or a `discordClientId` that isn't a Discord id stops Desktop at startup rather than being skipped.

The IPC socket also serves as the single-instance check (a socket that answers means Desktop is running; a dead one is replaced; launching again asks the running Desktop to show itself), and carries control requests from the CLI: `status`, `set userscripts on|off`, `debug on|off`, `allow <origin>`, and `disallow <origin>`, each with `--json`. If the TCP port is taken by something else, Desktop exits with an error saying so: without the port no browser can reach it. Where there's no IPC socket yet (Windows), that failed bind is also what stops a second Desktop.

## Settings and Status Without a Tray

Nothing requires a tray. The same status and settings are reachable four ways:

- **The extension's Settings** (popup and dashboard): the userscript setting, fetched from Desktop over the extension's own connection, and changeable from any connection Desktop knows is this OS user's. The extension shows Desktop's status and version, and on Settings > Platforms what Desktop's Discord adapter is doing, but no diagnostics; those (browsers, refused extensions, events) are Desktop's alone.
- **The popup**, which shows the connection and, when something's wrong, what to do about it (including the exact `allow` command for an unrecognized build).
- **The CLI** (`Parousia-Desktop status`, `set`, `allow`, `disallow`), and the same commands typed into the terminal Desktop runs in.
- **Notifications**, sent over the session bus whether or not a tray is showing: an unrecognized extension being blocked, and "Parousia Desktop is running" when it's launched a second time (so starting it from an app launcher always answers, even where there's no tray icon to click).

Desktop logs nothing by default: no output and no event history, until debug logging is turned on for the run (`--debug`, the tray's "Debug logging (this run)", `Parousia-Desktop debug on`, or the console). The switch is per process and never saved, so a normal run never pays for logging. Refused extensions are still tracked, since the tray's "Allow" and the popup's guidance rely on them.

## Desktop Tray

On Linux, Desktop is also a StatusNotifierItem (shown by KDE Plasma, and by GNOME with the AppIndicator extension, which Ubuntu enables by default). Its menu: a status line, a line per platform ("Discord: showing Jena Hub"), connected browsers with their identity, Diagnostics (the WebSocket's address and whether other OS users are refused, refused extensions each with an "Allow" action, recent events), Settings (checkmark toggles for userscripts and debug logging), and Quit. With no tray host running (stock GNOME), Desktop says so once and keeps working, sends its notifications anyway, and registers the icon if a tray host starts later.

The D-Bus side is written directly against the D-Bus specification (`desktop/src/tray/dbus.rs`: EXTERNAL authentication, message marshalling, both byte orders) rather than using `ksni`. Measured, a minimal `ksni` tray is a 1.59 MB stripped binary with 3.8 MB RSS and 5 threads, built from about 65 crates including `zbus` and an async executor. The hand-written client adds no crates and runs on the main thread blocked on the bus socket. Menu item ids are derived from content (connection ids for browsers, a hash of the origin for "Allow" items), so a click on a menu the panel rendered earlier can only ever act on what it showed, or on nothing. Verified against Plasma 6: it registers with the watcher, re-registers if the panel restarts, and Plasma fetches the layout and properties on every change.

On Windows, Desktop is a notification-area icon (it may sit under the `^` overflow arrow) with the same menu and balloon notifications for blocked extensions, written directly against Win32 (`desktop/src/wintray.rs`) on the main thread, blocked in the message loop. `--headless` runs without it. macOS has no tray yet: there, Desktop's console (`status`, `allow`, `disallow`, `userscripts on|off`, `debug on|off`, `quit` typed into its terminal), the CLI, and the extension's Settings cover the same ground.

## Compatibility Layer

Two separate compatibility targets, from `project/compatibility.md`:

- **PreMiD Activities.** Implemented: see PreMiD Activities under Activity System Architecture. An unmodified Activity's `presence.ts` (and `iframe.ts`) runs on Parousia's implementation of PreMiD's `Presence`/`iFrame` API, its `setActivity` calls feed the `ActivityRegistry`/`PresenceRuntime`, and its own Discord Application survives the translation. It stays a shim: PreMiD Activities never talk to Parousia's core directly, and their code is compiled unchanged from the source's `main` at build time.
- **Discord-RPC-Extension.** Lets Parousia's browser extension feed its detected `Presence` to Discord-RPC-Extension instead of Parousia Desktop, so someone can use Parousia's Activity detection without installing Parousia Desktop at all. Implemented, browser-side, in `browser/src/compat/discord-rpc-extension.ts` (Chromium and Firefox only; not the userscript, since Discord-RPC-Extension isn't published there). Confirmed against its actual source, not just `docs/api.md`: it isn't a network protocol, it's the browser's own cross-extension messaging. A compatible extension registers once with `chrome.runtime.sendMessage(<Discord-RPC-Extension's id>, { mode: 'active' | 'passive' })`; registering from a background script rather than a content script (exactly Parousia's shape, with no content script at all) always becomes their "background" presence type regardless of `mode`, per their own registration logic. It then answers periodic (~15s) presence requests, delivered via `chrome.runtime.onMessageExternal` (not `onMessage`, which is only for their separate content-script relay pattern), with `{ clientId, presence }` in Discord's Rich Presence payload shape. The `Presence` → Discord payload translation this needs is the one Desktop's Discord adapter uses. The two can't share code (TypeScript here, Rust in Desktop), so the mapping is one function per side with the same rules, both tested against `adapters/discord/activity-mapping.json` (see Platform Adapter Architecture). It does not feed back into Parousia's own canonical `Presence`/`Activity` types. Any extension can reach `onMessageExternal` by default; declaring `externally_connectable.ids` narrows that to just this one id, but only on Chrome (Firefox has never implemented `externally_connectable` at all, open since 2016, bugzilla.mozilla.org/1319168), so the actual cross-browser restriction is a `sender.id` check in code, not the manifest. **Remaining:** the protocol requires a Discord Application `clientId` to render anything in Discord at all, so the compatibility layer stays fully wired but inert (registers with nothing, answers nothing) until `DISCORD_RPC_EXTENSION_CLIENT_ID` is chosen. That's its own switch, separate from Parousia's Application id that the app link below falls back to. Once it is, `browser_specific_settings.gecko.data_collection_permissions` in `browser/manifests/firefox.json` already declares `browsingActivity` and `websiteContent`, because the extension hands Parousia Desktop an Activity's name and text, which reaches Discord. That covers this layer too, since it sends the same presence to another local program.

  **Its app, used directly.** Discord-RPC-Extension's own desktop half (`discord_rpc_ext` on Linux, its Node `server.js` elsewhere) is a WebSocket server on port 6969 with no authentication and no `Origin` check, listening on every interface. The extension sends it `{clientId, presence, extId}`, `{action: "disconnect"}` (on tab changes, even with nothing registered), `{action: "party"}`, and `{action: "reply"}`; the server sends `{version}` and forwards Discord's `join`/`joinRequest`/`spectate`. Parousia's extension now talks to that app itself (`browser/src/compat/discord-rpc-server.ts`), so Discord works without Parousia Desktop and without Discord-RPC-Extension's browser extension, locked down to plain Rich Presence: it only ever sends `{clientId, presence, extId}` (`extId` is required; without it the app throws on a new client id and exits) and `{action: "disconnect"}`, only after it showed something itself, so it never clears presence another tool set; of what comes back it reads only `{version}`; it resends a shown presence every 15 seconds, since the app clears one silent for 30; and it uses `127.0.0.1` only. It is a fallback, not a second route: it yields (no connecting, no probing, nothing shown, and what it showed cleared at once) until the Desktop link has failed to answer, and again the moment Desktop connects; while Desktop is being tried it keeps its last answer, so a retry or a first attempt can't make it flicker. A Desktop that refuses this build (`not_allowed`, `incompatible`) counts as not answering. Once it's the one showing, it connects on the same terms as the Desktop link (while a popup or dashboard is open, or while there's an Activity with a Discord client id to show, retrying every 10 seconds, letting go 30 seconds after the last need), and it's on by default, switched by Settings > Platforms (Discord, and "Discord-RPC-Extension"), where its status ("Looking for it…", "Connected", "Not running") lives. The dashboard's Overview mentions it only until Parousia Desktop is connected, since Desktop then shows Discord itself and the app stands down. Each Activity shows as its own Discord Application (`ActivityInfo.discordClientId`, like PreMiD's), falling back to Parousia's own. It stands in for Parousia Desktop rather than running beside it: while Desktop is connected, Desktop shows Discord itself, so this link sends nothing (the same presence twice would be two activities on the profile), and it takes over again when Desktop goes away. One side effect of the app's design: each new connection becomes the one its `join` events go to, so while Parousia is connected, Discord-RPC-Extension's browser extension misses party joins until it reconnects. Checked end to end against a stand-in server in a private network namespace (never a real running app). Parousia Desktop still deliberately does not answer on port 6969 as a drop-in for that server: doing so means accepting presence from any page or extension, the opposite of its link's security model.

## Website

The site (`parousia.abadima.dev`) lives in its own repository, [parousia-project/website](https://github.com/parousia-project/website), so it builds and deploys on its own and a documentation fix doesn't run this repository's CI. It's **Astro + Svelte 5**: Astro handles static pages, routing, and the Markdown documentation in one project, matching the "single consolidated project" goal in `project/vision.md`; Svelte is used for the one interactive piece, the download page's suggestion of the Desktop build for the visitor's system. The site is statically generated and deployed to GitHub Pages by its own workflow.

It has a landing page, Download, and Documentation (installation, configuration, Activities, compatibility, privacy and security, development), plus the standalone `/pwa/` page (see Full-Screen Presence View). The Activity documentation summarizes and links to the Activities repository's guide rather than copying it. Download links go to `releases/latest/download/<file>` in this repository, which works because the release workflow's file names carry no version (see `.github/CONTRIBUTING.md`, Releasing); the site's `src/site.ts` lists them and is the one place to change if a release file is renamed.

## Full-Screen Presence View

Beyond the popup, the extension has a larger presence view: a dashboard page (`browser/src/fullscreen/`), opened from a control in the popup. The popup and the dashboard render the Activity being shared through one module, `browser/src/shared/presence-view.ts`: plain DOM code that turns `{ activity }` into either an Activity card (name, details, state, a ticking elapsed clock) or an empty state, never a placeholder or a simulated one. Both resolve the Activity the same way, by asking the background script, so a PreMiD Activity that only its page script knows about shows up too.

The website's `/pwa/` page is a separate, static "no extension detected" screen that shares no code with the extension. It was built to share this renderer, but with no bridge to a running extension it only ever showed that one state, so it became plain markup. A live bridge would need web-page-to-extension messaging (`externally_connectable.matches` plus `chrome.runtime.connect`), which Firefox doesn't support at all (see the Discord-RPC-Extension note above), so it could only ever be Chromium-only. That's a real trust boundary and a real cross-browser gap to design around deliberately, so it's left for when it's actually needed.
